Cloud Foundry: Diego Explained By Onsi Fakhouri

September 3, 2014

This post was originally published on ActiveState’s blog. View the archived original.

Recently I met with Onsi Fakhouri who is the Product Manager, and previously a developer on Diego, the Cloud Foundry sub-project being jointly developed by Pivotal, IBM, SAP and Cloud Credo. Diego is designed to be a key piece of the Cloud Foundry project’s architecture which will replace other major components, such as the DEA (Droplet Execution Agent - where application containers live), the Health Manager and several responsibilities of the Cloud Controller.

Onsi joined Pivotal Labs back in 2010, prior to the Cloud Foundry project moving to Pivotal from VMware. He has worked on the Cloud Foundry project for the past 14 months, originally being assigned to working on the Health Manager.

Onsi led the development of HM9000 (Health Manager 9000) which is a replacement of the original Cloud Foundry Health Manager. This was a complete rewrite in Go and adds clustering support to Health Management in Cloud Foundry.

Defining Diego

While admitting he needed to work on his elevator pitch, Onsi said that Diego combines a scheduler, runner and health manager. It is a rewrite of the Cloud Foundry runtime. He said that, at its core, Diego is a distributed system that allows you to scale and run N instances of a process across a series of cells.

Diego is responsible for the uptime of applications. It can stream output from the application processes and ensures the routing of requests to those applications.

Why The Rewrite?

The reason for the rewrite, Onsi told me, is the same story with any rewrite. The existing code is hard to maintain and add features. In the case of the DEA and Health Manager, which Diego removes the need for, the code was too enmeshed with the Cloud Foundry code-base.

In Onsi’s CF Summit talk on Diego, which you can find on YouTube, he talks about the triangular dependencies between the Cloud Controller, the Health Manager and the DEAs.

Onsi’s team wanted to make this area of Cloud Foundry more modular and more generic.

Schedulers

At the core of Diego is a distributed scheduling algorithm which orchestrates where containers go and hence where application instance processes are run.

There are many open-source schedulers available, such as Apache Mesos or more recently Google’s Kubernetes. I asked Onsi if Diego was similar to these.

Onsi said that Mesos is optimized for “big data” workloads, whereas with Diego they are optimizing for application workloads.

The supply-demand relationship is also different between the two. For Mesos all worker cells report that “I am available to take N pieces of work” and Mesos decides where the work goes. In Diego an Auctioneer (of which there can be many) says “I have N pieces of work, who wants them?“. Diego’s worker cells then join an auction and the winning cell of each auctioned-off piece of work gets that piece of work.

Onsi describes Mesos’ approach as supply driven, or a “reverse-auction”, and Diego’s approach as demand driven. It’s “I have N things” vs “I have N availability”. He said it is a different approach and that he could not really say which was better or worse.

Amit Gupta gives a good reason for the auction approach in his post App Placement in Cloud Foundry Diego: A Classical Optimization Problem, when he says “…we have to take into account that between the time [the] system realizes it needs to make a decision about placing an app instance, and the time it takes action on a decision its made, the input it based its decision on may have changed.”

The “distributed mesh” they have created seems to be working well and they have done simulations to test it. These simulations allow them to quickly tweak the auction algorithm for computing scores. They now need to test whether it will work well at scale in the real world.

Tasks and LRPs

Diego can run two types of processes: Tasks and LRPs (long running processes).

Tasks are processes that are run once and have a finite running time. This might be a script or job to process a piece of data.

LRPs run continuously. This might be a web-server or some other service that continuously accepts input and processes it. LRPs only terminate due to intervention (stopped or killed) or failure.

Cells

Cells are where the Tasks and LRPs are run. These are most analogous to DEAs in the current Cloud Foundry architecture. You would generally have one Cell per VM.

Auctions

Where LRPs are run is decided by the Auction process and there are currently two auction types: LRPStartAuction and LRPStopAuction.

LRPStartAuctions occur when LRPs need to be assigned somewhere to run. Essentially, one of Diego’s Auctioneers is saying “We need another instance of this app. Who wants it?”

LRPStopAuctions occur when there are too many LRPs instances running for a particular application. In this case, the Auctioneer is saying, “We have too many instances of this app at index X. Who wants to remove one?”

The Cell that wins the auction either starts or stops the requested LRP.

Auctions For Tasks?

I was curious why Tasks were not included in Auctions and why there was such a distinction in Diego between the two. After all, both are processes that need to run somewhere. The only real difference if that LRPs run continuously whereas Tasks run for a finite amount of time.

Onsi said that this is historical and will change. To get Diego up and running they needed to write Tasks first. This provided the mechanisms for staging and bootstrapping a running application. Soon after came the LRPs and that is when they implemented the auctioning system. They applied it to LRPs, but not Tasks. Onsi said that it now needs to be applied to Tasks and then Tasks and LRPs will be closer in the way they are treated by Diego.

Standalone Diego

Diego has been decoupled from Cloud Foundry in such a way that it could be a standalone system.

The current interface to Diego places requests into etcd, but Onsi tells me that, “Once the primary customer (Cloud Foundry) is served, we can build an API around etcd. The path to this is short.”

He said that Diego could be packaged so that anyone could use it, for purposes beyond Cloud Foundry.

“You could deploy your own cluster of Diego and build your own layer on-top of it”.

Docker Backend

One of the selling points of Diego, is that you support various container backends, such as Windows or Docker.

Functionality is being added to enable end-users to push Docker images directly into a Cloud Foundry cluster running Diego.

IBM collaborated on the initial Docker implementation with the core Diego team at Pivotal, Colin Humphreys from Cloud Credo and Momchil Atansov from SAP. They worked from Pivotal offices up to the point where the integration points were agreed on. Now, Matt Sykes, Michael Fraenkel and Simon Leung of IBM continue to drive this development, while Pivotal focus on the core Diego implementation.

Onsi will soon publish a video which shows scaling up a Docker image based application across multiple VMs.

Windows Backend

CenturyLink, who contributed the IronFoundry project to Cloud Foundry, are working on the Windows backend for Diego.

Implementing A Backend

When Onsi’s team started thinking about Diego they realized that Cloud Foundry’s container implementation, Warden, made more sense if it was split in two. So they separated it into the API implementation and the actual container implementation. Therefore, there is often confusion when talking about what Warden is. Onsi admits that this confusion continues with Diego, as some components are named “Warden” when they should be “Garden” and vice versa.

This separation between API and actual containers is similar to how Docker has an API and also a container implementation, libcontainer. Note, that in the future, Garden may actually use Docker’s libcontainer implementation, but this depends on whether some Warden features can be merged into libcontainer.

How do you implement a backend in Diego? For example, a Diego backend to deploy LRPs to run processes directly within Amazon EC2 or Google Compute Engine instances.

Onsi said that there are 2 pieces of code that you need to implement that cover the platform specific components of Diego: Warden-Linux and Linux-Circus.

Warden-Linux implements an API for managing Garden containers. To support alternative containers, you would need to implement the same API to talk to the alternative containers interface.

Alternative implementations would follow a similar naming convention. For instance, Warden-Windows might be the Windows implementation.

The current support for Docker images is actually implemented in Warden-Linux. This is because Garden can directly mount the Docker image’s file-system layers. The resulting container is actually a Garden container, not a Docker container. Regardless, this means that the Docker image itself is portable and consumable by both Docker and Diego.

Circus

The Linux-Circus is the second half of the platform specific implementation. This encompasses three scripts called tailor, soldier and spy.

A tailor helps during staging to build the container specific to the application instance. The Linux-Circus tailor also knows how to run buildpacks.

A soldier helps with launching the platform specific application. A lot of its job is setting the environment variables correctly. Onsi tells me that it’s amazing how much of running an application is just getting the environment set up just right.

A spy helps with monitoring the application process running in the container. This script is periodically run inside the container and reports application instance health back to Diego.

Docker-Circus is a Docker-specific implementation of Linux-Circus. There is also a Windows-Circus in the Cloud Foundry incubator.

Go Diego, Go

In order to write a platform-specific container implementation for Diego, you will most likely want to learn the Go programming language. For instance, Warden-Linux is written in Go and ideally you will only want to implement the interfaces, rather than rewrite Warden-Linux entirely. Alternatively, you can implement the Go interface that talks to your implementation, which could be running in a separate process and communicating over HTTP or some other protocol.

Data Vs Communication

When Diego was first announced I got the impression that NATS was going away in favor of etcd. NATS seems to be a key component of Diego, so I asked Onsi what he thought about NATS and how it played a part in Diego.

Onsi told me that when they worked on HM9000 (the new clustered Health Manager) they put everything into etcd. This worked well. It was a nice way to build a distributed system and everything was globally visible. He said that eventual consistency is a data problem, not a communication problem and etcd handles this for you.

NATS is temporal, said Onsi. It’s a message bus and it can be lossy. For Diego auctions, lossy is acceptable and the system can tolerate it.

Onsi admitted that with Diego they put too much into etcd initially. For instance, a “start auction” announcement was placed in etcd. But this is not a statement of truth, he tells me. It’s a piece of communication. Therefore, it needs to be moved from being stored etcd to being communicated over NATS.

“etcd is the solid backbone of Diego”

Simulations

Diego includes simulations for testing the auction orchestration.

Onsi has a science background. Therefore, he valued the tight feedback loops they got with the auction algorithms. He wanted to know how these things work and how they performed.

“There’s order dependency everywhere. There are many places where you have to run A and then B and then C.”

Combine this with a large asynchronous distributed system and things get complicated quickly. Simulating this means it can be tested and reasoned about more quickly.

They can run the simulation either in-process or across multiple processes. They can also deploy the processes across a cluster, using BOSH, and test in places such as Amazon Web Services.

Onsi said that unit tests are great for isolation and integration tests exercise more pedestrian usage. “This [simulation testing] gives an us extra layer of testing.”

Onsi tells me that they originally tested five different algorithms and found a winner.

Complexity and Adoption

A concern I had was with the complexity of Diego. There are many moving parts and the communication between them is not simple. I asked Onsi if he had any concerns about whether this would hinder developer adoption of the Diego open-source project.

Onsi said that most developers would deploy Diego via BOSH. It is currently a cognitive burden and a practical burden. He said that unfortunately the Go community has not yet solved the dependency management problem.

Git is also not well designed for managing many small related components. Onsi said that there is some consideration as to whether one Git repository “to rule them all” would make more sense for Diego. He also said that they need to address the naming of components. “We’re currently in component naming alpha”. Good examples of this are ”TPS” and ”Nsync“.

Developer Workflow

“We try to run all tests locally before pushing. That includes unit tests and two layers of integration tests,” said Onsi.

These two layers are Inigo and the CF Acceptance Tests. Inigo is their integration test suite which only tests the Diego components. The CF Acceptance Tests incorporate the entire stack including the Cloud Controller.

To install Inigo you would run ”go get github.com/cloudfoundry-incubator/inigo”. This will fetch the integration suite and all its dependencies.

“Running it is a slightly more complex matter that involves running Concourse - an awesome CI system built by one of our developers”, said Onsi. “Concourse is shipped as a BOSH deployment. In our local dev flow, we spin up a Concourse deployment in a bosh-lite VM. This allows us to run Inigo from our Mac’s command-line in a container spun up by Concourse in the bosh-lite VM. We need to do this because Inigo exercises Warden-Linux which only works on Linux.”

“In my opinion, the only way to onboard is to pair [program]”, Onsi told me. “Open-source will give us good feedback.”

Super Releases

Currently, diego-release is a separate release to cf-release. To install Cloud Foundry with Diego, you first deploy cf-release and then deploy diego-release to the same BOSH Director.

Onsi said that it will continue this way for now, rather than merging diego-release into cf-release. Diego can be deployed as a standalone system, so it makes sense to have a separate deployment for it.

Instead, he thinks there should be a super release that includes other releases such as cf-release and diego-release. He sees other components, such as Loggregator warranting their own release, which would then also be included in a super release of Cloud Foundry.

Additional Features

They still have to get to feature parity with the existing DEA before they think about adding any new features.

In the future they would like to add console access to the container and more instrumentation around the app lifecycle.

Conclusion

The future for Diego is looking bright. As we saw in last week’s Cloud Foundry Advisory Board Meeting, Diego, via an experimental Diego CPI, can now be used as a distributed container platform on which to deploy Cloud Foundry components. How’s that for inception?

In the same meeting we also heard of a video Onsi is producing, which may be released before the post, that demonstrates deploying a Docker image to Diego, scaling it and watching Diego tolerate losing several of it’s VMs which host the Diego Cells.

We look forward to seeing Diego mature. Onsi tells me that they are hoping to have something concrete by the end of the year.

For more information, I recommend taking a look at the Diego Design Notes on GitHub, which gives a thorough overview of the components.
